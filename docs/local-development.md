# Local development

The current development baseline is a laptop with VS Code and directly installed services. Docker, Docker Compose, Kubernetes and MinIO are not required.

## Required JavaScript workstation

- Git
- Node.js 25.9.0
- npm 11.6.2
- VS Code (preferred)
- Access to the Dotin Nexus npm repository

Run:

```bash
npm run workstation:check
```

The workstation check validates Node `>=25.9.0 <26`, npm `>=11.6.2 <12`, and Git. It intentionally does not fail because PostgreSQL is missing; database prerequisites are validated separately with `npm run db:check`.

## npm workspaces

The root `package.json` owns the workspace list:

```text
apps/*
packages/*
```

Turborepo remains the task orchestrator. npm is the only package manager for the active workstation baseline. Do not create or commit `pnpm-lock.yaml`.

The canonical dependency lockfile is `package-lock.json`. It must be generated by npm 11.6.2 against the required Nexus and committed only after install/lint/typecheck/test/build validation succeeds.

Before dependency installation or after editing any workspace manifest, validate metadata:

```bash
npm run workspace:check
```

This checks that every workspace has a valid `@interview/*` name, a valid semantic version, and exact versions for internal workspace dependencies.

## Required npm registry

This repository is intentionally pinned to:

```text
https://nexus3.dotin.ir/repository/Dotin-NPM/
```

The root `.npmrc` is committed so `npm install` and all workspace dependency resolution use this Nexus. Do not override the registry to `registry.npmjs.org` during normal development.

Before installing packages, verify both the effective npm configuration and Nexus package access:

```bash
npm run registry:check
```

The `.npmrc` keeps TLS verification enabled and applies bounded retry/timeout settings for the internal Nexus.

If Nexus authentication is required in the developer environment, configure credentials only at the user/machine level or via environment variables. Never commit tokens, passwords, `_auth`, or `_authToken` values.

Installation analytics from Scarf are disabled at the root package level.

## Clean npm recovery

A previous pnpm checkout, or a workspace manifest change after an npm lockfile was generated, can leave a stale local dependency graph. Known symptoms include:

```text
npm error Invalid Version:
Cannot find module '<workspace>\\node_modules\\typescript\\bin\\tsc'
Cannot find module '<workspace>\\node_modules\\tsx\\dist\\cli.mjs'
```

Use the repository recovery command:

```bash
npm run install:clean
```

The command:

1. validates workspace metadata;
2. removes root `node_modules`;
3. removes every `apps/*/node_modules` and `packages/*/node_modules` tree left by a previous package-manager/install state;
4. removes the local `package-lock.json`;
5. runs a fresh `npm install` using the committed Dotin Nexus configuration.

If a clean install still fails, do not keep deleting state repeatedly. Preserve the npm debug log and fix the dependency/version problem in the repository.

## NestJS tooling on Node 25

NestJS 12 remains the API framework. The Nest CLI and schematics are intentionally not part of this local toolchain because their current Angular-devkit dependency excludes Node 25.

The API uses:

```text
TypeScript compiler -> dist/
Node.js 25 -> dist/main.js
```

Development watch is implemented by `apps/api/scripts/dev.mjs`, which runs the local TypeScript compiler through npm and restarts the compiled API after a clean compilation.

The shared ESLint rule requiring type-only imports is intentionally not applied to Nest API source files as a blanket rule: constructor-injected Nest classes must remain runtime value imports so emitted decorator metadata can preserve DI tokens. Do not auto-fix those imports to `import type` without verifying the injection token is explicit.

Do not re-add `@nestjs/cli` or `@nestjs/schematics` without first validating Node 25 compatibility.

## PostgreSQL

PostgreSQL 18.x is required for database/API persistence work, not for the frontend-only visual review or static lint/typecheck/build path.

Install PostgreSQL locally when entering database/API validation. Create a local database and role using your preferred PostgreSQL administration tool.

Suggested development values:

```text
host: localhost
port: 5432
database: interview
user: interview
```

Keep the password only in `.env`; never commit it.

Example connection string:

```text
postgresql://interview:CHANGE_ME@localhost:5432/interview
```

Validate PostgreSQL only when it is installed/configured:

```bash
npm run db:check
```

## Starting the apps

Frontend-only visual development:

```bash
npm run registry:check
npm run workspace:check
npm install
npm run workstation:check
npm run dev:web
```

Or use `npm run install:clean` instead of `npm install` when recovering from a stale dependency tree.

Full local stack after PostgreSQL is configured:

```bash
npm run db:check
npm run db:migrate
npm run dev:bootstrap
npm run dev
```

## Quality gate

```bash
npm run lint
npm run typecheck
npm run test
npm run build
```

## Add services only when needed

- Redis: when ephemeral state/caching/workflow features require it.
- pgvector: when semantic candidate matching begins.
- Python: when AI/media workers begin.
- LiveKit/coturn: when realtime interview development begins.

Local file artifacts are stored under `.local-data/` and are ignored by Git.
